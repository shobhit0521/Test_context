Task: "which functions call F?" — the atom of code navigation an agent performs constantly.
  • Graph only is the most precise (93.3%) and needs zero verification, but misses callers (recall 82.8%).
  • Traditional only reaches full recall but is noisy (precision 89.0%) and forces the agent to vet 4.3 candidate hits/question.
  • Combined keeps full recall (100.0%) while cutting candidates-to-verify by 69% (4.3 → 1.3).
Neither tool alone is best. The graph is a precise, zero-cost backbone; traditional search closes the recall gap; together they give complete context with the least review effort.

Method

  • Ground truth: jedi static resolution of every in-repo call site of F (import/alias/scope aware), independent of the system under test.
  • Graph only: CALLS edges from the graph built by the real build_graph MCP tool.
  • Traditional only: grep for F(, each hit mapped to its enclosing function (includes false positives from comments, strings, same-named attribute calls).
  • Combined: graph edges ∪ grep hits.
  • Effort: candidate hits an agent must verify — all grep hits for traditional; only grep hits not already confirmed by the graph for combined; zero for the graph.
  • Sampling: most-connected functions per repo; only functions with ≥1 real caller are scored.

Honest limitations

  • The graph's recall gap comes from static-analysis blind spots (dynamic dispatch, some method calls) — exactly why traditional search remains necessary.
  • Grep's recall is high for text call sites; its precision/effort cost is the price the graph removes.
  • Keys are normalized to relpath::simple_name; rare same-name collisions in one file are possible.
